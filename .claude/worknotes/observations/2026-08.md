# Observations — 2026-08

## AAR — skill-composite drift and the doctrine/capture seam (2026-08-01)

### Finding 1 — Skill-composite drift is invisible until an unreferenced script is invoked

RF's `.claude/skills/artifact-tracking/` was missing 21 files that its own `SKILL.md` and the
`planning` `SKILL.md` referenced, including the entire IntentTree-sync family
(`intenttree_capture.py`, `intenttree_sync.py`, `stamp-plan-binding.py`, `stamp-node-slug.py`,
`verify-slug-roundtrip.py`, `backfill-node-evidence.py`, `what-shipped.py`, 4 shared `_*.py`
modules, 6 test modules, `CHANGELOG.md`, `intenttree-sync.md`).

**Why it matters.** Discovered only because a plan-frontmatter lint was attempted and the script
was absent — nothing in the repo checks that a skill's referenced files actually exist. Per
`agentic_meta_dev/docs/ARTIFACT-UPSTREAM-REGISTRY.md` line 68, `artifact-tracking` is deliberately
NOT globally symlinked — per-project copies only, canonical edit point
`agentic_meta_dev/.claude/skills/artifact-tracking/`. That design makes silent per-project drift
the default failure mode, not an edge case.

**How to apply.** When a skill reference fails to resolve, do not treat it as one missing file —
diff the whole composite against its registry-declared upstream first. Fix via additive-only sync:
never overwrite a file present on both sides, since per-project adaptations are intentional. Fixed
this way in RF commit `c4308e4`; 9 files that differ on both sides were left alone as deliberate RF
adaptations.

### Finding 2 — Plan doctrine and the IntentTree capture tooling disagree, and the failure is a silent success

`intenttree_capture.py` sync mode hard-requires a `tasks[]` frontmatter list
(`feature_from_file()` L237-248 returns `None`; `main()` L400-403 prints "no tasks[] in <file>;
nothing to sync" and **returns 0**). Current plan doctrine
(`planning/references/plan-doctrine.md`) authors Tier 2/3 plans with `wave_plan.phases[]`
milestones and deliberately no `tasks[]`.

**Why it matters.** Every doctrine-conformant Tier 2/3 plan captures ZERO nodes and reports
success. Observed live: a Tier 2 RF plan imported as a SourceArtifact with 0 nodes / 0 edges; the
node had to be created by hand with `itt node create`. The skip branch is untested — the only test
file (`scripts/tests/test_intenttree_capture_slug.py`) covers slug-stamping only. There's also a
real design gap sizing this at ~5 pts: `wave_plan.phases[]` carries no per-phase `status`, and
`_collect_task()` L204 defaults to `not_started`, so milestones would import permanently
not-started unless a phase-completion source is decided first.

**How to apply.** After any `itt sync import` / `intenttree_capture.py` run, verify the node
COUNT, not the exit code — exit 0 with zero nodes is the expected output for a milestone plan
today. Contract authored at
`agentic_meta_dev/docs/project_plans/feature_contracts/infrastructure/intenttree-capture-wave-plan-milestones.md`
(commit `588c212`).

### Finding 3 — Two frontmatter tools, opposite churn profiles

`validate-plan-frontmatter.py --apply` edits surgically: normalizing one plan's `status: draft` ->
`status: not_started` + `planning_maturity: draft` produced a 2-insertion/1-deletion diff with no
reserialization. This is the OPPOSITE of `manage-plan-status.py --status/--field`, which
re-serializes the whole frontmatter block (~231 lines of churn for a one-field flip, per the
existing memory entry on this tool).

**Why it matters.** The standing "use surgical Edit, not the CLI, for plan frontmatter" rule does
NOT extend to the linter — `--apply` is safe, including for a bulk sweep. RF's own
`plan-frontmatter-schema.md` §5.2 declares `status` as the lifecycle enum with `planning_maturity`
DERIVED from it and `maturity` a MAY-alias the linter consolidates — so the ~53 RF plans carrying
`status: draft` are non-conformant aliases, not a competing house convention. Bulk sweep was not
run this session (advisory linter, mostly `completed` historical plans); offered to the operator.

**How to apply.** Prefer `validate-plan-frontmatter.py --apply` over hand-editing status fields;
keep avoiding `manage-plan-status.py` for plan/PRD frontmatter.
