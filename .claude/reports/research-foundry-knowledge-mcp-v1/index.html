Feature report · research-foundry-knowledge-mcp-v1

Research Foundry Knowledge MCP — Local Read-Only Knowledge Plane

Research Foundry now has a local, read-only Knowledge MCP: a governed way for local AI agents and tools to search and fetch RF's own knowledge — sources, assertions, reports, and runs — through a standard Model Context Protocol surface, plus matching CLI and read-only HTTP routes. Every read passes an access-policy gate before any data is projected, hidden records are indistinguishable from missing ones, and a negative-matrix test suite proves reads cause zero writes and zero provider calls. The plan shipped all six phases (P1–P6) and squash-merged to local main as 1376e85; 433 focused tests, ruff, and mypy are green as of this report, with karen and task-completion-validator gates approved during execution. This v1 is deliberately schema-aligned-only (stdio + loopback), NOT OpenAI/ChatGPT compatible and with no remote transport. One dependency-hygiene finding (KMCP-F1) is documented and deferred, and the work is on local main only — not yet pushed to origin.

What was delivered

The problem

RF's knowledge lived behind files, a catalog database, and an assertion ledger with no safe, uniform way for an agent or external tool to ask 'what does Research Foundry know about X?' Anything wanting to read RF knowledge had to reach directly into files or the database — which risks accidental writes, index rebuilds, cross-workspace leakage, and exposure of raw paths or secrets. There was no policy-gated, read-only, contract-stable retrieval surface.

The solution

A single policy-first KnowledgeAccessService fronts four governed projectors (source, assertion, report, run) and a search/fetch composer, exposed through three read-only transports that all return the same governed shape: an independent stdio MCP process (rf-knowledge-mcp) with exactly eight tools, an rf knowledge CLI, and GET-only /api/knowledge routes. The core search{query} and fetch{id} contracts are frozen; RF-specific snippets, paging, filters, and receipts live under separately named rf_* tools so the core contract stays stable. IDs are opaque (rfk:v1:<kind>:<opaque>) and URLs are loopback-only and explicitly non-canonical.

What changed

MCP process

A new standalone program, rf-knowledge-mcp, that speaks the Model Context Protocol over stdio and offers exactly eight read tools.

Technical detail: Independent OS process with its own registry/settings/credential allowlist and a lazy FastMCP import. Tools: search, fetch, rf_search, rf_fetch, rf_source_get, rf_assertion_get, rf_report_get, rf_run_get. Entry point rf-knowledge-mcp = research_foundry.knowledge_mcp.process:main. Inventory + transport lock asserts no Streamable HTTP/SSE/OAuth/non-loopback options.

Findings

deferred

KMCP-F1 — rf-knowledge-mcp transitively requires the serve extra (fastapi), not only mcp

Importing research_foundry.knowledge_mcp.process pulls fastapi/starlette/uvicorn into sys.modules via two module-level imports in knowledge_access.py (AuthIdentity and the load-bearing resolve_workspace_isolation_active), both routed through api/__init__.py's unconditional fastapi probe. A purely mechanical TYPE_CHECKING move fixes only half; a full fix would relocate auth types out of research_foundry.api.* — a structural change touching catalog/builder/AgentJob call sites, out of scope for a P6 hardening pass.

Impact: An operator installing only research-foundry[mcp] (no serve) hits ModuleNotFoundError: fastapi at import time rather than the hand-written missing-SDK message. AC KMCP-1's actual forbidden set (Search Router/Operator registries, provider creds, mutators) remains genuinely absent — verified by the transitive-closure test — so this is a dependency-hygiene gap, not an AC violation or regression.

Remote/OpenAI-ChatGPT compatibility is deliberately out of scope for v1

The local profile is declared schema-aligned-only. A local-profile truth gate labels loopback URLs non-canonical across CLI/API/docs and rejects remote config; docs and schemas carry no OpenAI/ChatGPT compatibility claim. Remote Streamable HTTP/OAuth, canonical HTTPS URLs, remote cache isolation, and shared/vector/graph retrieval are each linked to a shaping spec with explicit promotion evidence gates.

Impact: Integrators must treat this as a local plane only. Any 'ChatGPT connector'-style use requires the deferred remote transport + canonical-URL work (KMCP-DF-1/DF-2) to land first with its own review.
